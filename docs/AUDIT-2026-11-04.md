# Аудит навігації та музичних можливостей — 2026-11-04

## Межі

Аудит поточного робочого дерева Vey 0.1.48; код продукту не змінювався. Знахідки з коду — не доказ відтворення зависання. Історичні результати в інших документах не вважаються новими перевірками. Робоче дерево вже містило багато незакомічених змін.

## Навігація: підтверджено кодом, вплив потребує профілювання

1. `src/app.rs::on_navigate` викликає `refresh` синхронно після зміни сторінки. `refresh` перебирає видимі треки, планує обкладинки, формує чергу, вибрані треки й колекції медіатеки та оновлює моделі. Під час пошуку обкладинок плейлистів він також шукає трек у каталозі для кожного плейлиста. Фонова обробка зображень сама по собі не усуває витрат цієї роботи на UI-потоці.
2. `src/web.rs` має аналогічне синхронне оновлення, включно з побудовою колекцій. Для категорій альбомів і артистів `LibraryViewState::collections` групує і копіює треки; для альбомів також сортує вміст. Робота виконується і при переході на іншу сторінку, якщо обрано відповідну категорію медіатеки.
3. Сортування медіатеки за останнім прослуховуванням у `src/services.rs::LibraryViewState::apply` сканує історію всередині компаратора сортування. На великих бібліотеках та історії це потенційно дороге місце, але жодного вимірювання цього конкретного шляху ще немає.
4. `examples/navigation_latency.rs` встановлює `active_view` без виклику контролера застосунку, використовує 300 синтетичних рядків і не завантажує обкладинки чи аудіо. Він вимірює рух Slint, а не повну вартість переходу з реальними даними. Браузерний тест навігації заглушує API; його час охоплює також Playwright і міст, а не лише рендеринг.
5. Перевірка software-renderer кутів у `examples/navigation_transition.rs` охоплює піксельне обрізання до переходу; старий збій не доводить причину зависань. Android потребує окремого вимірювання на пристрої.

## Узгоджене джерело даних

Уточнена вимога користувача: для Vey каталогу використовувати наявні внутрішні запити YouTube Music; Spotify account/OAuth прибрати, лишити лише імпорт публічних Spotify playlist і перетворювати композиції на YTM IDs. Не будувати Spotify artist/catalog integration через Development Mode/Web API і не розширювати приватний Spotify access. YTM InnerTube/WEB_REMIX уже використовується для public каталогу. Spotify embed metadata не є стабільним API; поточний імпортер відмовляє на 100-row межі, де повноту неможливо перевірити.

Внутрішні формати не є стабільним контрактом: вони можуть змінитися або вимагати активної сесії. Не обходити автентифікацію, CAPTCHA, paywall, регіональні/акаунтові обмеження чи rate limits. Spotify імпорт читає тільки публічні embed metadata, не бере cookies і не має обходити внутрішній web anti-abuse flow; помилка формату означає fail closed. YTM приватна бібліотека лишається окремим explicit desktop browser flow. Токени й cookies не логувати, не передавати в WASM чи публічний backend та не включати до Vey cloud sync. Методи й поля внутрішніх відповідей артистів/альбомів ще не підтверджені живим probe.

## План усунення проблем і додавання функцій

### Етап 0 — відтворення та базові виміри

**Робота:** додати instrumentation навколо кліку/навігаційного callback, синхронного `refresh`, побудови колекцій, виставлення моделей і першого/останнього кадру. Записувати розподіли p50/p95/max, довжину UI callback, число оновлених рядків, запитів і декодованих обкладинок. Логи мають бути вимкненими за замовчуванням і не містити назв файлів, токенів чи URL із підписаними параметрами.

**Сценарії:** холодний старт; повторне відкриття; швидкий retarget трьох маршрутів; Library Songs/Albums/Artists/Playlists; сортування за історією; 300/2k/10k треків; 0/2k/10k записів історії; обкладинки в кеші й поза кешем; грає локальний трек і YTM stream; повільний/помилковий backend. Windows GPU та software, браузер із production WASM на 4181 fixture і Android debug build на реальному пристрої/AVD. У кожному звіті зазначити версію, renderer, розмір viewport, живлення, фонові процеси, профіль даних і п'ять повторів після прогріву.

**Готово, коли:** відомо, чи затримка походить від навігаційної анімації, синхронного контролера, моделі Slint, браузерного bridge, рендерера, I/O чи їх комбінації; є порівнювані звіти й відтворюваний сценарій.

### Етап 1 — швидкі й правильні переходи

**Робота:** виправляти лише гарячі ділянки, підтверджені етапом 0. Очікувані кандидати: не перебудовувати колекції/чергу/selection на переході, коли їхні залежні дані не змінилися; кешувати колекції за ревізією Store і параметрами фільтра/сортування; побудувати індекс `track identity → last played` один раз перед сортуванням замість повторного проходу історії в компараторі; не шукати cover-track повторно для кожного playlist при незмінній медіатеці; створювати видимі моделі ліниво. Фонові операції мусять отримувати незмінний snapshot та generation ID; старі результати скасовувати/ігнорувати, актуальні likes/download/art продовжувати розсилати у всі активні alias rows.

**Приймання:** на тих самих fixture-наборах p95 UI callback не перевищує 16 ms на еталонному ПК і не росте непропорційно між 2k та 10k; p95 від кліку до першого руху <50 ms, settlement відповідає запланованим 160–180 ms плюс максимум два кадри. Для кожної платформи окремо; якщо Android клас пристроїв не може досягти межі, задокументувати клас/режим і показати безперервне відображення прогресу. Швидкий retarget завжди завершується на останньому маршруті. Після сортування, фільтра, scan, like, download і relink усі рядки лишаються актуальними.

**Перевірка:** native controller-level fixture, що викликає той самий callback `on_navigate`; браузерний fixture на зібраному WASM з API stub; Android UI/perf capture; великі бібліотеки; без мережі й з повільною мережею. Вимір до/після і окремий regression для cache invalidation/generation cancellation.

### Етап 2 — сторінки артистів

**Інтерфейс даних:** внутрішній typed `ArtistPage` із стабільним provider ID, назвою, необов'язковою обкладинкою/аватаром, top tracks, альбомами, пов'язаними артистами та cursor для продовження. Кожен підрозділ може бути відсутній або порожній; UI не вигадує біографію, популярність чи кількість слухачів. Browse ID YTM з Home передається напряму; локальний артист лишається локальною колекцією.

**UI/поведінка:** картка артиста й artist result відкривають профіль із кнопкою Play/Shuffle, Top tracks, Albums та Related artists лише коли є дані. Запам'ятовувати scroll і шлях назад. Додати skeleton, retry, offline/cache стан, порожній стан і недоступний артист. Кожен запит обмежений таймаутом, кількістю елементів і скасуванням при новому browse ID.

**Залежності/ризики:** live probe для artist/album pages стосується YTM InnerTube/WEB_REMIX. Spotify artist/catalog pages не входять у вимогу. Для Spotify playlist лише публічна embed metadata; точний title/artist/duration match до YTM, fail closed на невідповідності, приватних даних чи зміні HTML. Не додавати Spotify account login, cookie import або обходи anti-abuse. Зберігати безпечні YTM fixtures й показувати лише підтверджені поля. Не з'єднувати Spotify IDs з YTM без прозорого match confidence.

**Приймання/перевірка:** parser fixtures для різних варіантів renderer, відсутніх полів, недоступного ID і continuation; живий публічний probe без приватних даних; Home→артист→альбом→трек→назад на Windows/web/Android; кеш, повтор, швидке перемикання двох артистів і помилкова мережа.

### Етап 3 — повні альбоми й плейлисти

**Робота:** відокремити моделі `AlbumPage` та `PlaylistPage` від масиву треків; додати заголовок/артиста/дату/обкладинку лише за наявними полями, Play all, сортування лише якщо джерело дозволяє, cursor і дозавантаження при прокрутці. Зберігати ID та джерело елемента. Для playlist імпорт уже зберігає порядок і повтори; continuation у browse має мати дедуплікацію token, hard cap, скасування та не замінювати валідний кеш неповною відповіддю.

**Приймання/перевірка:** понад одну сторінку, дублікати, unavailable row із video ID, порожня/приватна/видалена колекція, цикл токенів, timeout, retry і перехід до іншої колекції до відповіді старої. Порядок та повтори не змінюються. Застосувати ті самі сценарії в desktop, web і Android.

### Етап 4 — пошук і керування бібліотекою

**Робота:** повертати typed search results (song/artist/album/playlist/video) з provider identity та destination; зберегти локальний миттєвий пошук і debounce 280 ms; не змішувати однакові назви різних сутностей. Інвентаризувати й виправити заявлені прогалини Android file picker/SAF, browser file reselection, прогрес/скасування завантажень, settings parity та accessibility браузерного Slint shell окремими задачами.

**Приймання/перевірка:** пошук змішаних сутностей, неоднозначні назви, Enter під час pending query, скасування застарілої відповіді, offline, 500 локальних результатів; Android grant/deny/revoke і round-trip файлу; браузер reload/relink; download abort без часткового файлу; keyboard/screen-reader test для сторінок у scope.

### Етап 5 — черга, рекомендації та Spotify-подібні зручності

**Робота:** додати історію навігації shuffle (попередній/наступний саме в порядку фактичного прослуховування), детерміноване перемішування на початку сесії/черги та правила повтору, не перемішувати під час кожного next; перевірити відновлення черги. Покращення рекомендацій робити як окремі локально вимірювані зміни: пояснюване «чому рекомендовано», виключення артистів/треків, repeat/skip feedback, ручне оновлення та надійний порожній/offline стан.

**Інтеграційні межі:** Spotify account/OAuth прибрано; лишається public playlist import → YTM `yt://` tracks. Відтворення Spotify audio, private playlists, artist catalog і Spotify account sync поза scope. YTM private library має desktop browser flow; web та Android мають інші межі. Не переносити сторонні токени в Vey cloud sync.

**Приймання/перевірка:** unit fixtures для повторів, shuffle history, видалення поточного/наступного треку та відновлення; ручні сценарії queue editor з активним playback; рекомендації оцінювати на зафіксованому fixture наборі без передачі приватної історії в публічний каталог.

## Велика мапа розвитку плеєра

Це дерево можливих робіт для всього Vey, а не обіцянка вмістити кожен пункт у наступний реліз. Позначення: **P0** — основа якості/надійності; **P1** — завершити вже початі сценарії; **P2** — великі нові можливості після стабілізації. Роботи на зовнішніх внутрішніх API починати з короткого spike та перевірки доступності даних.

### Гілка A — швидкість і стабільність (P0)

- Повний профіль переходу: від вводу до першого кадру, довжина UI callback, p50/p95/max, бібліотеки 300/2k/10k і мережеві/обкладинкові стани.
- Віртуалізація довгих списків і обкладинок; лінива побудова неактивних сторінок; кеш колекцій з чітким invalidation.
- Індекс історії/ідентичностей для сортування й пошуку; уникати повторного сканування каталогу на кожному переході.
- Межі фонового навантаження: concurrency, байти, таймаути, backpressure; пріоритет поточного треку та видимих обкладинок.
- Відновлення після завислого/помилкового запиту, втрати мережі, призупинення застосунку й швидкого скасування.
- Прибрати software-renderer залежність від точних пікселів там, де різниця субпіксельна; залишити поведінкову перевірку обрізання й окремі допуски для renderer.

**Готовність гілки:** зафіксований end-to-end baseline на кожній доступній платформі, немає UI callback довше 100 ms на цільових синтетичних наборах, дані не стають застарілими після паралельного scan/navigation. Поріг 16 ms для звичайних callback — ціль, а не припущення про всі Android пристрої.

### Гілка B — навігація та щоденний UX (P1)

- Єдина модель маршруту/назад/вперед для Home, Search, Library, Explore, деталей та Now Playing; зберігати scroll і фільтри при поверненні.
- Глобальна черга навігації без втрати позиції: артист → альбом → трек → назад; відкривати зовнішній URL/плейлист у правильному контексті.
- Повні empty/loading/error/offline стани з Retry; не очищати робочий контент до успішного завантаження нового.
- Швидкий доступ: клавіатурні команди desktop, пошук із будь-якої сторінки, контекстне меню треку, зрозумілий статус виконання довгих дій.
- Узгодити кнопки, назви й поведінку на вузькому екрані, планшеті та desktop; прибрати зайві рухи, що не допомагають зрозуміти зміну стану.

**Готовність гілки:** клавіатура, pointer і touch проходять однакові головні сценарії; Back відновлює точний попередній список і scroll; системна кнопка Android Back не закриває застосунок замість повернення з деталі.

### Гілка C — каталог, пошук і музична відкриваність (P1 → P2)

- Типізований каталог результатів: пісня, відео, артист, альбом, плейлист; зберігати provider ID, джерело, назву, арта й destination.
- Повна сторінка артиста: Top tracks, albums/EPs/singles, пов'язані артисти, відео та доступна інформація профілю; показувати тільки поля, які реально повернув сервіс.
- Повна сторінка альбому: контекст артиста, дата/тип релізу за наявності, список треків, Play all, пов'язані релізи.
- Повна сторінка плейлиста: автор/опис/обкладинка за наявності, кількість і порядок треків, продовження, помітні недоступні позиції.
- Глобальна черга пошуку, фільтр за типом, історія останніх запитів із приватним локальним зберіганням та очищенням.
- Підказки пошуку, автодоповнення й вкладки каталогу тільки коли це не створює повторні повільні запити; кешувати коротко й скасовувати застаріле.
- Пов'язані результати: «від артиста», «схожі артисти», «альбом до цього треку», «версії треку» — лише якщо джерело дає стабільні ID.
- Видимі YTM/local match groups із ручним виправленням; для Spotify лише точна playlist-import відповідність, не об'єднувати різні версії/виконання автоматично.

**Готовність гілки:** стабільний typed contract, пагінація без втрати порядку/повторів, невірний або відсутній renderer не валить екран, шлях назад працює після повільного запиту. Внутрішній YTM transport використовує наявну WEB_REMIX основу; Spotify не постачає artist/catalog transport.

### Гілка D — медіатека і локальна музика (P1)

- Звести Local/Downloads/Liked/Playlists у послідовні правила джерел та пояснювати, чому трек видимий/недоступний.
- Перевірити великі сканування: інкрементальний rescan, скасування, дублікати, зміна/видалення файлів під час скану.
- Редагування метаданих, обкладинок і кількох треків пакетно; undo для руйнівних тегових змін; dry-run перед перейменуванням/перенесенням.
- Надійне relink після переміщення папки, повторного вибору файлу у web та відновлення недоступного Download без видалення збережених playlist/likes.
- Android SAF round-trip для читання/запису; окрема перевірка permission grant/deny/revoke і MediaStore змін.
- Вебтеги: fixtures MP3/FLAC/Ogg/Opus/MP4, некоректні/великі файли, арта з обмеженням байтів; прогрес і відміна довгого import.
- Backup/restore: preview, конфлікти, міграції, контроль цілісності та зрозумілий шлях rollback.

**Готовність гілки:** не губляться посилання, likes, черги та playlist при переміщенні джерела; файли користувача не видаляються приховано; Android/Web сценарії перевірені у своєму середовищі.

### Гілка E — відтворення та черга (P1)

- Підтвердити play/pause/seek/volume/end-of-track на WASAPI, Android output і browser audio; перевірити Bluetooth і перемикання виходу.
- Доробити стани Loading/Buffering/Unavailable/Retry; у черзі лишати позицію недоступної пісні з причиною, не ламати наступні елементи.
- Справжня історія shuffle, previous/next, repeat-one/all, зміна режиму посеред черги й відновлення після restart.
- Queue tools: add next, move, remove, clear upcoming, save queue as playlist, прибрати дублікати за запитом; не стирати навмисні повтори.
- Кілька форматів і тривалостей: variable bitrate, невідома тривалість, великий файл, seek поза діапазоном, короткий track, stream/cache collision.
- Gapless/crossfade — тільки після перевірки рушія і окремого UX перемикача; не ламати точний lyric/audio clock.
- Медіаклавіші, системний Now Playing, Android MediaSession і browser Media Session повинні мати синхронний стан із чергою та фактичним аудіо.

**Готовність гілки:** контракт одного джерела правди між аудіорушієм, Queue, UI та OS controls; жодного завислого worker після cancel; точний seek і коректне відновлення після sleep/network failure.

### Гілка F — інтеграції та облікові записи (P1 → P2)

- Спільна модель провайдера без змішування публічного каталогу, приватної бібліотеки й локальних файлів.
- YouTube Music: розширити чинний браузерний connect flow сторінками артиста/альбому та приватними даними лише там, де явна сесія дає доступ.
- Spotify: залишити public playlist URL import і точне перетворення у YTM tracks; account connection, private sync та Spotify playback не реалізовувати.
- Показати стан підключення, останню синхронізацію, помилку, строк життя сесії та кнопку reconnect; disconnect має зупиняти майбутні запити, не видаляючи імпортовані дані без явної дії.
- Додати імпорт кількох playlist за раз і звіт зіставлення: збіги, неоднозначні, відсутні, повтори, локальні/подкастові елементи.
- Будь-який write-back у сторонній сервіс, remote playback або account-wide sync залишити окремим проєктом із явним запитом користувача, дослідженням доступу та rollback.
- Provider adapter-и мають ізольовані parser fixtures, version marker, health status і контрольовану деградацію; не логувати запити, що містять сесію.

**Готовність гілки:** авторизація належить користувачу, сесія не залишає його пристрій без явної причини; відмова/expiry не затирає дані; зміна внутрішнього API помітна й не призводить до часткового тихого імпорту.

### Гілка G — функції для слухача (P2)

- Smart playlists: нещодавно додані/непрослухані/часто пропущені/за артистом/за локальною папкою; правила видимі й редаговані.
- Розширена черга: зберегти поточну сесію, наступні треки, автододавання схожих композицій із вимикачем.
- Локальні теги настрою/жанру, рейтинги, позначки explicit та власні колекції; все працює offline.
- Історія з фільтрами/очищенням/пауза-історії; користувач керує строком зберігання і синхронізацією.
- Рекомендації з поясненням причини та ручним виключенням; не надсилати локальні сигнали до provider без окремого opt-in.
- Відображення credit/composer/release/version/lyrics sources там, де є перевірені метадані.

**Готовність гілки:** кожна персональна функція має вимикач, локальний режим і зрозумілий контроль над історією; рекомендації мають оцінювані fixture приклади, а не лише суб'єктивне «виглядає розумно».

### Гілка H — кросплатформність, доступність і візуальне доведення (P1)

- Windows: GPU/software порівняння, DPI 100/125/150%, мінімізувати/відновити, різна ширина, медіаклавіші.
- Android: реальний телефон плюс emulator smoke; rotation, cutout, IME, Back, lifecycle, battery saver, Bluetooth, permissions, SD/SAF.
- Web: Chrome/Edge, touch/keyboard, reload/relink локальних файлів, same-origin API offline/error, browser history, малий viewport.
- Аудіювати читання canvas shell screen reader-ом; визначити доступний DOM маршрут для основних дій або чітко обмежити недоступні поверхні.
- Перевірити контраст, focus-visible, screen reader labels, reduced motion, масштаб тексту й локалі для всіх основних екранів.
- Уніфікувати контрольовані screenshot fixture-и без крихких абсолютних RGBA assertions на різних renderer; окремо лишити точні regressions для шрифтів/матеріалів, де це обґрунтовано.

**Готовність гілки:** ключові сценарії мають платформні свідчення, а скріншот headless browser не видається за Android acceptance.

### Гілка I — прибрати, спростити, переробити

Цей список — кандидати на видалення після перевірки залежностей, telemetry/usage за наявності та migration plan. Не видаляти дані чи керування користувача тільки заради візуальної чистоти.

- **Прибрати мертві альтернативи:** дубльовані/недосяжні callback-и, невикористані transport-и та повторні parser шляхи — після пошуку всіх feature flags, tests і release scripts.
- **Оновити тестові harness-и:** прибрати фіксовані координати у користувацьких діях, чекати ролі/ідентичність елемента; синхронізувати ліміти обкладинок із кодом; renderer-specific tolerances замість flaky піксельного порівняння.
- **Згорнути дубльовані моделі:** єдиний typed collection/search result і один індекс identity; видалення старих adapters лише після native/WASM parity.
- **Спрощувати рух:** вилучати streak/blur/ambient декор тільки якщо профіль показав його внесок і якісний A/B підтвердив, що користувач не втратив орієнтацію. Уже наявні 100–180 ms переходи не змінювати без нових вимірів.
- **Зняти тимчасові diagnostics:** `VEY_LEGACY_*` flags, debug routes, probes — після двох релізів зі стабільним replacement і задокументованим rollback; не прибирати поки вони потрібні для порівняння.
- **Прибрати повторні мережеві запити:** нормалізувати provider cache key і TTL; не кешувати приватні відповіді довше/ширше, ніж дозволяє користувач.
- **Видаляти непідтримувані фічі лише за критеріями:** немає працездатного джерела, неможливо безпечно підтримувати, дублюється кращим потоком, або не використовується — і є міграція даних та повідомлення користувачу.

**Готовність гілки:** перед видаленням є список залежностей, перевірка migration/backup, regression на альтернативних платформах і явний перелік поведінки, яку втрачає користувач.

### Пропонований порядок великих релізів

1. **Reliability:** гілки A + H smoke blockers; зафіксувати контрольований повний navigation benchmark і Android runtime.
2. **Catalog completion:** гілка C для YTM artist/album/playlist та typed search, спершу тільки дані з підтверджених внутрішніх відповідей.
3. **Player completion:** гілки D + E: локальна медіатека, стабільна черга, стан джерел і відновлення.
4. **Provider boundaries:** гілка F: прийняти точність і межі public Spotify import; Spotify account/catalog expansion не входить до поточного scope.
5. **Personalization:** гілка G: smart playlists і рекомендації з приватними локальними сигналами та вимикачами.
6. **Simplification:** гілка I після adoption/compatibility аналізу та успішних замін.

Кожен великий реліз має окремо пройти native, browser та Android acceptance, parser fixtures, migration/restore, offline/error path і перевірку часу переходів. Невиконана платформа явно лишається відкритою, а не зараховується за схожим desktop тестом.

### Релізні ворота для кожного етапу

- Не включати чужі локальні зміни та не переписувати дані Store без версійованої міграції й backup/rollback тесту.
- Для native і WASM збирати спільні типи; окремо зібрати Android APK та перевірити запуск на реальному пристрої/емуляторі.
- Всі асинхронні результати прив'язати до generation/request ID; обмежити timeout, кількість сторінок/байтів і concurrency; помилка мережі зберігає останній валідний кеш.
- Перед випуском повторити baseline етапу 0, пройти regression навігації, сторінок, queue/playback, локального збереження та безпечного відновлення; публічну мережу, пристрій і збірку називати перевіреними лише коли вони реально були запущені.

## Фактичні перевірки

- Windows 11 Pro 10.0.26200, Intel Core i5-12400F: свіжозібраний release `navigation_latency`, 300 синтетичних треків, 1100×760, дев'ять маршрутів: перші 5 px через 8,8–44,2 мс, завершення через 167,1–197,0 мс, p95 інтервалу event loop 23,9 мс, максимум 82,8 мс. Один запуск; вимірює ізольований UI, а не повну дію контролера. Звіт: `target/audit-20261104-navigation/report.json`.
- Свіжозібраний release `navigation_transition` з `SLINT_BACKEND=winit-software` знову провалив точне порівняння пікселів внутрішнього кута до першого переходу: `[15, 18, 16, 255]` проти `[16, 17, 16, 255]`. Після panic процес довелося зупинити. Це підтверджує збій тесту, але саме по собі не встановлює помітний візуальний дефект чи причину зависання.
- Свіжозібраний debug WASM, headless Edge: `test:navigation-latency` пройшов, включно зі швидким перенаправленням, мобільним viewport і перевіркою відсутності повноекранних readback. Таймінги тесту містять браузерний міст і Playwright; під час запуску також компілювався нативний fixture, тому це не чистий benchmark і не порівняння платформ. Звіт: `target/audit-20261104-web-fresh/report.json`.
- `test:artwork-fetch` пройшов обмеження розміру й тайм-ауту. `test:artwork-queue` на свіжому WASM завершився тайм-аутом: очікує шість фонових обкладинок, тоді як `src/web.rs::pump_artwork` обмежує їх двома та резервує третій слот. Тому тест застарів і не перевірив резервний слот.
- Оригінальний `test:player-performance` на свіжому WASM зупинився на кліку рядка вподобань: скриншот показує кнопку вподобання в іншій позиції. Тимчасова копія під `target/` зі зміненою координатою пройшла для 2 000 синтетичних треків: play/pause, next/previous, seek, вподобання через навігацію, вибір після видалення рядка, 60 подій гучності, flush і перезавантаження. Це перевірка поведінки, не замір затримки переходу й не перевірка реального аудіопристрою.
- ADB не показав підключених пристроїв, `emulator -list-avds` не повернув налаштованих AVD. Android runtime, реальна бібліотека, реальні обкладинки під час переходів і живі відповіді сторінок артистів не перевірені.
